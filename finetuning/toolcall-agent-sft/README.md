# Tool-Call SFT for Long-Running Autonomous Agents (LFM3-1.7B)

Fine-tune **LFM3-1.7B** to emit structured `<tool_call>` actions for an autonomous
game agent, and run the whole pipeline on an **8 GB AMD RDNA1 GPU** (RX 5700 XT,
gfx1010) with QLoRA. Peak VRAM measured **1.42–3.77 GiB** depending on sequence
length and dataset size (see [Measured results](#measured-results)).

> All data in this example is **synthetic and generated by the included script**.
> No real player data, credentials, or environment-specific paths are included.

---

## Why this example

Most LFM fine-tuning examples target chat: the model generates free-form text turn by
turn. That works for dialogue, but in a **long-running agent loop** (hundreds of
consecutive decisions with near-identical context) free-form generation is prone to
repetition and parsing failures.

This example instead trains the model to emit only LFM3's native `<tool_call>` format
as its action space. A companion service parses the tool calls and executes them.
Constraining the output to a fixed action vocabulary greatly reduces malformed
output and removes the need for heuristic action parsing; chat can be handled
separately. This is a prompt/format-level mitigation, **not** a guarantee — malformed
calls are still possible and should be counted in evaluation.

The dataset generator deliberately includes two regimes:

| Regime | Share | What it teaches |
|---|---|---|
| **Instruction** | 50% | map a player command ("cut some wood") to a tool call |
| **Autonomous (AUTO)** | 50% | with no instruction, inspect the state and decide on an action |

The AUTO regime is the important one: it teaches the model to act proactively
(gather, craft, protect, retreat) instead of idling.

## Measured results

Tested on RX 5700 XT 8 GB, Windows 11, Python 3.12, ROCm 7.14.1, torch 2.11 +
rocm7.14.1. Values below are reported per configuration; they are **not** from a
single run.

| Config | grad_norm | Peak VRAM | Status |
|---|---|---|---|
| fp16 LoRA (AMP on) | NaN | 3.41 GiB | broken on RDNA1 |
| fp32 LoRA (AMP off) | 12.36 → 7.73 | 6.63 GiB | works |
| QLoRA NF4, seq 512 (64 examples) | 10.62 → 7.56 | 1.42 GiB | works |
| **QLoRA NF4, `train_qlora.py`, seq 640 (64 ex / 5 steps)** | — | **3.77 GiB** | **verified with this script** |

A separate **full task run** (original project, same QLoRA NF4 / fp32-compute config)
used 4,000 synthetic examples with `max_length=640`, LoRA r=32, 1 epoch / 375 steps,
batch 4:

- train loss **1.609 → 0.078**, token accuracy **0.735 → 0.975**, grad_norm finite throughout
- peak VRAM **3.24 GiB**, ~43 min on the single RDNA1 GPU
- saved adapter reloaded cleanly with `PeftModel.from_pretrained`

Peak VRAM varies substantially with sequence length and how the examples are tokenized
(note that 1.42 GiB, 3.24 GiB and 3.77 GiB come from different runs/configurations).
The default `max_length=1024` in `train_qlora.py` may use more than any figure above —
size your own run accordingly.

The fp16 failure and the RDNA1 root cause are documented in the companion guide
`finetuning/amd-rdna1` (PR #153): RDNA1 lacks bf16 and dot-product instructions and
the MIOpen CK grouped-conv kernel is absent for gfx1010; fp16 AMP produces NaN
gradients. Disable AMP / use fp32 compute with 4-bit weights.

## 1. Dataset design

`build_dataset.py` generates `sft_dataset.jsonl` with 4,000 examples. Each example is
a 3-message chat (`system`, `user`, `assistant`).

**System prompt** declares an action vocabulary and hard rules, e.g.:

```
## Available actions (<tool_call> format)
  chat, follow_entity, attack_nearest, flee, gather, craft_and_equip,
  craft_bed, sleep_in_bed, eat, move_to, look_at, jump, stop_moving, ...

## Autonomous decision rules
- hostile mob + HP > 8  -> attack_nearest
- hostile mob + HP <= 8 -> flee
- no tool in inventory  -> gather logs/stone, then craft_and_equip
- night, but players still awake -> DO NOT sleep; keep them company
- ...
```

**User message** is a compact state snapshot:

```
Position: (..)  Health: ../20  Food: ../20
Time: ....  IsNight: ...  Weather: clear
Inventory: ...
Nearby entities: Player@(..), zombie(id=..)@(..)
DANGER (hostiles): ...
Nearby beds: ...
<!! HOSTILE NEARBY !! / !! LOW HEALTH !! / !! NIGHT !! alerts>
```

**Assistant message** is one or more native tool calls only:

```
<tool_call><function=gather><parameter=block_name>oak_log</parameter>
<parameter=count>5</parameter></function></tool_call>
<tool_call><function=craft_and_equip><parameter=item_name>wooden_pickaxe</parameter>
</function></tool_call>
```

Action coverage (counts over the 4,000 examples) spans all nine action types, with
the AUTO regime dominating so the model learns initiative rather than just Q&A.

Run:

```bash
python build_dataset.py                 # writes ./data/sft_dataset.jsonl
python build_dataset.py --n 400 --out ./data/small.jsonl   # quick smoke run
```

Use `--seed` for reproducibility. See `sample_data.jsonl` for eight representative
examples (all synthetic).

## 2. Format alignment (the subtle part)

LFM3 ships its own chat template and an optional "thinking" mode. Two details matter:

1. Use LFM3's **native** `<tool_call>` syntax in the assistant messages. Inventing a
   JSON action format forces the model to learn a new output convention and converges
   more slowly.
2. Call the tokenizer with `enable_thinking=False` so training and inference use the
   same template:

```python
text = tok.apply_chat_template(
    messages, tokenize=False,
    add_generation_prompt=False,
    enable_thinking=False,   # must match the inference service
)
```

A mismatch here is a common cause of "training loss goes down but the deployed model
outputs nonsense".

## 3. Training

`train_qlora.py` uses NF4 4-bit weights with fp32 compute, LoRA `r=32, alpha=64`,
`target_modules="all-linear"`, AdamW, gradient checkpointing, and `max_length=1024`.
bf16 and fp16 are both disabled (`bf16=False, fp16=False`) — required on RDNA1.

```bash
pip install torch==2.11.0+rocm7.14.1 ...   # see Environment below
pip install transformers peft trl datasets accelerate bitsandbytes

python train_qlora.py \
  --data ./data/sft_dataset.jsonl \
  --out  ./out/agent-sft \
  --steps 1200 --save-steps 300
```

Checkpoints are saved every N steps so an interrupted run is not lost. The script
prints `torch.cuda.max_memory_allocated()` at the end.

### Patching a single hard rule afterwards (optional)

If the base SFT model still fails one specific rule (e.g. "only sleep when the player
sleeps"), a small **override adapter** is cheaper than retraining:

- ~660 focused examples, 1 epoch, LR `5e-5`, starting from the existing adapter via
  `PeftModel.from_pretrained(..., is_trainable=True)`;
- takes ~3 min on the same GPU and leaves the rest of the behaviour intact.

The included dataset generator can emit such a focused set with `--profile sleep`.

## 4. Evaluation

Two complementary checks:

1. **Offline**: load with `PeftModel.from_pretrained` and verify a handful of held-out
   states produce the expected tool calls (see `sample_data.jsonl`).
2. **Online**: run the model behind a decision service and drive an agent for 100+
   consecutive turns. Track: malformed tool calls, garbled output, and whether AUTO
   turns produce a physical action rather than a chat reply.

For reference, a separate decision-model experiment (using a structured-output model
rather than this fine-tuned LFM3) ran 67 consecutive turns with 0 garbled outputs.
That result is **not** from the LFM3 adapter produced here; it is included only to
illustrate why a constrained action vocabulary is attractive for agent loops.

Reproduced with:

- GPU: AMD RX 5700 XT 8 GB (gfx1010 / RDNA1)

- torch `2.11.0+rocm7.14.1`, torchvision `0.26.0+rocm7.14.1`

```bash
export AMDGCN_USE_BUFFER_OPS=0   # required for ROCm on gfx1010
export TORCHDYNAMO_DISABLE=1
```

`HSA_OVERRIDE_GFX_VERSION` is **not** needed with the multi-arch ROCm wheels.
